# Устройство приложения

## Frontend: от опубликованного документа до страницы

`src/domain/content.ts` описывает типизированный документ сайта: компанию, общую тему, упорядоченные секции и элементы карточек. Функция перестановки создаёт новый массив и не меняет закешированную версию сервера.

`src/store/api.ts` содержит единую точку работы с API — RTK Query. Теги обновляют черновик, публичный контент и заявки после изменений. Access JWT хранится в Redux только в памяти. Refresh JWT хранится в HttpOnly cookie; браузерный JavaScript не читает его. При истечении access выполняется один общий refresh-запрос: параллельные запросы ожидают его, чтобы не использовать один refresh-токен несколько раз при ротации. CSRF-защита включена для cookie-аутентификации login/refresh/logout.

`pages/PublicSite.tsx` собирает шапку, навигацию, страницы и подвал. `components/SectionRenderer.tsx` переводит тип секции в соответствующий блок по композиции референса. Реестр ограничен понятными типами вместо произвольного HTML: редактор не может внедрить исполняемый скрипт через текст. React экранирует текст; `dangerouslySetInnerHTML` не используется.

`pages/Admin.tsx` держит локальную копию документа. Изменение поля затрагивает эту копию. Сохранение передаёт документ и ожидаемую версию; публикация — отдельная команда. Фоновые обновления RTK Query не заменяют несохранённые правки. Preview использует тот же renderer, что и публичный сайт: отдельная имитация дизайна не требуется.

`components/Privacy.tsx` управляет выбором cookies и региона. Геолокация вызывается только после отдельного согласия и нажатия кнопки; точные координаты используются в памяти браузера для выбора ближайшего города и не уходят в API. Неопределённый/далёкий город предлагается выбрать вручную. `components/LeadForm.tsx` отправляет имя, телефон, текст запроса, город и версию отдельного согласия.

## Backend: граница контента и атомарные команды

`cms/models.py`: `SiteContent` — агрегат редактируемой страницы с черновиком, публичной копией и версиями. `ContentRevision` — журнал сохранений и публикаций. `Lead` хранит заявку и свидетельство согласия. `MediaAsset` описывает загруженный файл; содержимое хранится через Django Storage в локальной папке или MinIO.

`cms/serializers.py` валидирует контракт документа и формы. Ограничены количество секций, размеры текстов, диапазоны цветокоррекции, шрифты, форматы цветов и URL медиа. Дубли ID не допускаются. Заявка без согласия, с неактуальной версией документа, неверным телефоном или заполненным honeypot не сохраняется.

`cms/services.py` выполняет изменение документа в транзакции. SQL `UPDATE ... WHERE revision = expected` реализует сравнение версии и запись одним запросом; если версия уже изменилась, результат не записывается и API возвращает 409. Изменение контента и запись истории коммитятся вместе. Сохранение черновика не затрагивает публичную копию.

`cms/views.py` отвечает за HTTP: права сотрудника, JWT, CSRF, загрузку файлов и вызов команд. Публичными остаются опубликованный документ, config с языками и лимитами загрузки, health/CSRF и создание заявки. Для входа и формы заявки заданы ограничения частоты. В dev cache локален процессу; production использует общий Redis между Gunicorn workers. Throttling DRF приблизительный и не заменяет ограничения на reverse proxy.

`config/settings.py` выбирает инфраструктуру по переменным окружения. Без PostgreSQL/S3 используются SQLite и локальные файлы. Production не запускается с встроенным development-секретом. `management/commands/seed_content.py` валидирует начальный документ и создаёт его один раз, сохраняя правки при повторном запуске.

## Почему здесь нет отдельного сервиса для каждой сущности

Это модульный монолит с одной предметной областью — корпоративный сайт и управление его содержимым. Представление, валидация, команды и хранение разделены. DDD применён к агрегату контента и границам команд, без дополнительных слоёв-обёрток вокруг Django ORM. Более сложный каталог с остатками, заказами, оплатой и интеграцией ERP потребует отдельных моделей и модулей, а не расширения JSON карточек до бухгалтерской системы.

## Инфраструктура

Nginx отдаёт frontend и направляет `/api/` в Gunicorn, `/storage/` в MinIO. Это сохраняет единый origin и позволяет работать без CORS. PostgreSQL и MinIO изолированы внутренней Compose-сетью; наружу выведены только web и локальная консоль MinIO. Контейнер backend работает от непривилегированного пользователя. Медиа имеют ограничивающий CSP, веб-интерфейс — CSP без внешних скриптов. MinIO собирается из зафиксированного upstream commit, поскольку готовые community-образы недоступны. Команда `init_storage` ожидает готовности S3 и создаёт bucket с политикой чтения объектов через boto3.

uv устанавливает Python-зависимости из lock-файла; npm ci делает то же для frontend. CI проверяет разные уровни: бизнес-инварианты и права API, типы и сборку React, утилиты frontend, поведение в браузере. Compose не является готовой конфигурацией высокодоступного production: миграции нескольких реплик следует выносить в отдельную release-команду, БД резервировать, MinIO и PostgreSQL мониторить.

## Языки и валидация редактора

Русская версия остаётся в `document.company` и `document.sections`, казахская — в необязательном `document.translations.kk` с такими же полями. `theme` общий. Одна revision и одна транзакция охватывают обе версии. Это позволяет читать старые документы без миграции и не смешивать параллельные изменения разных языков. `LocalizedContentSerializer` проверяет одну локаль, `DocumentSerializer` проверяет весь агрегат. Неизвестные коды перевода отклоняются.

`frontend/src/i18n/` содержит словарь интерфейса и известных демонстрационных текстов. Если сохранён перевод KZ, используется именно он; без него известные demo-строки переводятся, пользовательские строки остаются исходными. `localizedDocument` формирует представление, `withLocalizedDocument` записывает изменения только выбранного языка. В редакторе хранится полный документ, а не подменённая локализованная копия; сохранение и публикация отправляют весь агрегат. Выбор посетителя хранится в localStorage, атрибут lang страницы обновляется.

Клиентская проверка в `domain/validation.ts` помогает найти неверные поля до запроса. Серверная проверка остаётся обязательной: дубликаты ID, длины, цена, телефон, email, цвета и медиа-ссылки проверяются до ORM. Ошибки ограничений БД возвращаются как 409, временная недоступность БД — как 503 с Retry-After; SQL в ответ не попадает. Это обработка отказов, а не обещание исключить инфраструктурные ошибки валидацией полей.

Лимиты фото/видео читаются из env; `/api/config/` сообщает их редактору. Nginx создаёт свой лимит запроса из тех же значений при запуске контейнера. Production на одном VPS описан отдельно в `deployment.md`: Caddy завершает TLS, Nginx и Gunicorn остаются внутри сети, данные и сертификаты хранятся в volumes.
