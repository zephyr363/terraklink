# Контейнеры: состав и обновление

| Сервис | Основа | Почему |
|---|---|---|
| backend | `python:3.13-alpine`, несколько стадий | В runtime только Python, зависимости и код |
| web | `nginx:1.28-alpine` | Node/npm остаются в стадии сборки |
| PostgreSQL | `postgres:17-alpine` | Сохраняется текущая основная версия БД |
| MinIO | `alpine/minio:RELEASE.2025-10-15T17-29-55Z` + digest | Готовый образ вместо Go-сборки проекта |
| storage-init | `alpine:3.22` | Короткая подготовка владельца корня тома, затем выход |
| Redis / Caddy, production | `redis:7.4-alpine` / `caddy:2-alpine` | Кеш и HTTPS остаются в production-проекте |

`alpine/minio` публикуется проектом [alpine-docker/minio](https://github.com/alpine-docker/minio),
это сторонний образ. Версия и multi-arch digest проверены через
[страницу издателя](https://hub.docker.com/r/alpine/minio). `latest` не используется.
Полное значение по умолчанию находится в обоих Compose-файлах; его можно
переопределить переменной `MINIO_IMAGE` после проверки другого образа.

У опубликованного бинарника `minio --version` выводит `DEVELOPMENT.GOGET`.
Поэтому идентификатором сборки служит digest образа, а не эта строка.
Это фиксированный выпуск, а не обещание автоматических исправлений upstream.

## Владельцы файлов и существующие данные

Проверены владельцы работающих томов: backend использует `1000:1000`,
MinIO — `100:101`. Эти UID/GID сохранены; MinIO явно запускается под `100:101`.
Сервис `storage-init` меняет владельца
только каталога `/data` на подключённом томе — без рекурсивного изменения файлов,
удаления данных или создания нового bucket. Это также позволяет запустить пустой
том, поскольку каталог готового образа принадлежит root.

Если данные привезены с другого сервера и имеют другой UID, сначала проверьте
права на отдельной копии. Автоматического рекурсивного `chown` проект не делает.
Compose ждёт успешного завершения подготовки перед стартом MinIO. Bucket и
политику чтения объектов, как прежде, создаёт `init_storage` через S3 API.

## Из чего состоит backend

- `dependencies`: uv читает `pyproject.toml` и `uv.lock` с `--frozen --no-dev`.
- `test`: добавляются pytest/Ruff; используется в CI для проверки musl/Pillow/
  psycopg и PostgreSQL. Это отдельная цель сборки, она не развёртывается.
- `runtime`: копируется venv, запускается непривилегированный пользователь.
  В нём нет uv, npm, Go, компилятора и dev-зависимостей.

`infra/backend-start.sh` выполняет production-проверку, ожидание S3/подготовку
bucket, миграции, первоначальное заполнение и сбор статики. При ошибке останавливает
запуск. Затем через `exec` передаёт процесс Gunicorn. Его параметры можно задать
через `GUNICORN_WORKERS` (по умолчанию 3) и `GUNICORN_TIMEOUT` (60 секунд).

На проверенной машине размер backend через `docker image inspect .Size` уменьшился
с 374 520 916 до 158 696 182 байт (около 58%). Готовый MinIO примерно того же
размера: 159 499 891 вместо 157 333 067 байт; выигрыш здесь — отсутствие собственной
Go-сборки. Размеры несжатые, зависят от платформы и версий базовых слоёв.

## Проверка и обновление

```powershell
docker compose config --quiet
docker compose pull minio storage-init
docker compose build backend web
docker build --target test -f backend/Dockerfile -t terraklink-api:test .
docker run --rm terraklink-api:test
```

Перед заменой работающих контейнеров остановите приём записей и сделайте полную
копию по [инструкции](deployment.md#резервные-копии-обновление-и-восстановление).
Затем `docker compose up --no-build -d --wait`. Проверьте вход, чтение медиа,
загрузку на отдельной QA-копии и возможность резервирования. Томам сохраняются
прежние имена; `down -v` не используется. Не обновляйте основную версию PostgreSQL
простой заменой тега без процедуры миграции.
