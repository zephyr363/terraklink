# TERRAKLINK

Демонстрационный сайт производителя кирпича на основе https://likolorpro.ru, адаптированный для Казахстана. Основная композиция референса: оранжевая верхняя полоса, белая шапка, горизонтальная навигация, широкий баннер, преимущества, каталог, портфолио, консультация, информация о компании и акции. Фотографии и рекламные баннеры референса используются для локального согласования; это не действующие предложения TERRAKLINK.

Стек: TypeScript, React, Redux Toolkit, RTK Query; Django, DRF, JWT; PostgreSQL, Gunicorn, MinIO, Nginx, Docker Compose, GitHub Actions. Python-зависимости управляются **только uv**, фиксируются в `uv.lock`. npm и `package-lock.json` используются для frontend.

## Локальный запуск без Docker

Нужны uv, Node.js 24 и npm. Команды PowerShell из корня проекта:

```powershell
uv sync --frozen
$env:DJANGO_DEBUG='1'
uv run backend/manage.py migrate
uv run backend/manage.py seed_content
uv run scripts/setup_dev.py
uv run backend/manage.py runserver 127.0.0.1:8000
```

В другом терминале:

```powershell
cd frontend
npm ci
npm run dev
```

Сайт: http://127.0.0.1:5173. Редактор: http://127.0.0.1:5173/admin. Логин `editor`; случайный пароль находится в `.local/admin-password.txt`, исключённом из Git. `setup_dev.py` не меняет пароль существующего пользователя. Этот пользователь — локальный суперпользователь; для клиента создайте отдельного staff-редактора без прав суперпользователя.

SQLite и локальный каталог медиа используются только для разработки. Seed-команда не перезаписывает существующие изменения. Не выполняйте `seed_document.py` для обновления опубликованного сайта — изменяйте его через редактор.

## Запуск Docker Compose

Нужен запущенный Docker Desktop с Linux-контейнерами или Docker Engine.

```powershell
uv run scripts/prepare_env.py
docker compose config --quiet
docker compose up --build -d
docker compose exec backend python manage.py createsuperuser
```

Сайт и редактор: http://localhost и http://localhost/admin. TerraKlink Admin: http://localhost/django-admin/. MinIO Console доступна только на локальном интерфейсе http://localhost:9001; вход — переменные `MINIO_ROOT_USER` и `MINIO_ROOT_PASSWORD` из `.env`. Автоматически созданный `.env` предназначен для локального окружения.

Для уже созданного локального пользователя `editor` можно вместо интерактивного `createsuperuser` выполнить `uv run scripts/setup_docker_editor.py`: пароль передаётся контейнеру через stdin и не попадает в аргументы команды. Скрипт разрешён только при `DJANGO_DEBUG=1` и не меняет существующего пользователя.

PostgreSQL и MinIO хранят данные в именованных volumes. Bucket создаёт команда `init_storage` через S3 API; публично доступны только чтения объектов, а не список bucket. Медиа читаются через Nginx `/storage/`; API работает через тот же origin, CORS не требуется. В контейнере зависимости устанавливаются `uv sync --frozen --no-dev`, Gunicorn запускается из созданного uv окружения.

Community-репозиторий MinIO архивирован, официальные registry-образы при проверке недоступны. Поэтому Compose собирает MinIO из официального исходного commit `7aac2a2c5b7c882e68c1ce017d8256be2feea27f` с сохранением LICENSE/NOTICE. Первая сборка дольше обычного, требует доступа к GitHub и Go module proxy. Для production отдельно оцените поддержку и обновления безопасности MinIO; автоматического перехода на другой S3-продукт в проекте нет.

Для сервера в Казахстане: домен и HTTPS на внешнем reverse proxy, `DJANGO_DEBUG=0`, новые секреты, корректные `DJANGO_ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, `S3_PUBLIC_DOMAIN`. В исходном Compose web привязан только к loopback. Если TLS завершается перед Nginx, настройте доверенные proxy-заголовки строго для собственного proxy. Production-настройки TLS, резервного копирования и мониторинга зависят от выбранного хостинга и ещё не настроены.

## Работа редактора

1. Войти в `/admin`.
2. Выбрать секцию, изменить заголовок, текст, шрифт, цвета, яркость и насыщенность.
3. Загрузить фото/видео или изменить ссылку; в списке элементов отредактировать карточки и баннеры.
4. Переставить секции стрелками, скрыть ненужные или добавить новую секцию.
5. «Сохранить» записывает черновик. «Предпросмотр» показывает текущие изменения.
6. «Опубликовать» сохраняет изменения, затем переносит черновик в публичную версию.

Редактирование заблокировано во время сохранения/загрузки, чтобы не потерять промежуточные изменения. При конфликте версий сервер возвращает 409; сначала сохраните нужный текст отдельно, затем загрузите актуальную версию кнопкой в сообщении об ошибке. История редакций доступна в TerraKlink Admin только для чтения; интерфейс отката пока не реализован. Фото/видео удалённой секции автоматически не удаляются из хранилища, чтобы не сломать другие ссылки.

Фото: JPG/PNG/WebP до 10 МБ, с проверкой декодирования и размера. Видео: MP4/WebM до 50 МБ, с проверкой сигнатуры контейнера. Это не полная проверка видеокодеков и не антивирус. Для потокового воспроизведения больших файлов в production нужна отдельная обработка видео. Медиа в bucket публичные; не загружайте документы с персональными данными.

Заявки сохраняются в БД, отображаются в панели; статус и удаление доступны в TerraKlink Admin. Отправка email/SMS клиенту или менеджеру не подключена. Реальные платежи и корзина с оформлением заказа не входят в эту демонстрацию.

## Проверки

```powershell
$env:DJANGO_DEBUG='1'
uv run pytest --cov=cms --cov-report=term-missing
uv run ruff check backend
uv run backend/manage.py makemigrations --check --dry-run
cd frontend
npm run build
npm test
npm audit --audit-level=high
npx playwright install chromium
npm run test:e2e
```

Для браузерных тестов должны работать оба локальных сервера и существовать локальный редактор. В CI пароль берётся из `E2E_EDITOR_PASSWORD`. Тест публикации меняет тестовый заголовок и восстанавливает исходный после успешного прохождения: **не запускайте e2e на рабочем сайте клиента**. Тест заявки оставляет явно тестовую заявку в локальной БД.

GitHub Actions проверяет backend на PostgreSQL, frontend-сборку, unit-тесты, npm audit и браузерные сценарии. Workflow `Verify` включён в GitHub; он настроен для push, pull request и ручного запуска. Для ручного запуска откройте Actions → Verify → Run workflow и выберите нужную ветку.

Объяснение модулей и принятых решений: [docs/architecture.md](docs/architecture.md). Требования Казахстана и границы проверки: [docs/compliance.md](docs/compliance.md). Результаты фактически выполненных проверок: [docs/verification.md](docs/verification.md).

## Языки и production

Локальный Nginx по умолчанию доступен на `http://localhost:80`; порт 8080 оставлен совместимым адресом. Порты задаются `WEB_PORT` и `WEB_COMPAT_PORT`. При смене основного адреса обновляйте `S3_PUBLIC_DOMAIN` и `CSRF_TRUSTED_ORIGINS` в локальном `.env`; production использует отдельную конфигурацию.

В шапке сайта доступны русский и казахский языки; выбор сохраняется в браузере. В редакторе «Язык контента» переключает независимые версии секций и контактов, оформление общее. Публикация атомарно публикует обе версии. При отсутствии перевода переводятся только известные демонстрационные строки; произвольный контент остаётся исходным до редактирования KZ.

Лимиты загрузки задаются `MAX_IMAGE_UPLOAD_MB` и `MAX_VIDEO_UPLOAD_MB` в env-файле. После изменения пересоздайте backend и web. Production на VPS с HTTPS, проверка настроек и резервирование: [docs/deployment.md](docs/deployment.md).

## Версионирование

Исходный код ведётся в публичном репозитории [zephyr363/terraklink](https://github.com/zephyr363/terraklink): ветки `main` и `dev` отправлены на GitHub и отслеживают соответствующие ветки `origin`. `dev` используется для разработки и коммитов по завершённым этапам, `main` — для стабильных релизов. Рабочая ветка — `dev`; проверенные изменения переносятся в `main` через pull request в рамках явно запрошенного владельцем релиза. Правила сохранены в `AGENTS.md`.

По решению владельца серверная защита `main` **не включена**. Порядок работы соблюдается командой: прямой push в `main` не используется, изменения рассматриваются через pull request после успешных CI jobs `api` и `web`. Этот порядок описан в `AGENTS.md`; GitHub автоматически не запрещает его обход.

Перед коммитом после добавления нужных файлов в индекс:

```powershell
uv run --frozen scripts/check_staged_secrets.py
git diff --cached --check
git diff --cached --stat
```

Проверка ищет попадание локальных данных, совпадения с реальными секретами из `.env` и файла локального пароля, а также характерные сигнатуры ключей и токенов. Это дополнительная проверка, а не универсальная гарантия обнаружения любых секретов; staged diff нужно просматривать вручную. `.env.example` содержит placeholders, явно тестовые пароли в tests/CI не используются для рабочего окружения.
